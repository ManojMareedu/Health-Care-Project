## 1. Project context

Academic Healthcare Analytics project (UT Dallas) predicting a Medicare-style patient's
total claim charge and charge-cost tier from synthetic claims data. Currently exists as
a Python notebook (`Healthcareprojectfinal.ipynb`) that does data engineering, plus an

## 2. Business framing (keep in README)

Predicting which patient claims will land in high-charge tiers lets payers and hospital
finance teams flag high-risk claims for utilization review before they're settled,
route claims intelligently (complex/high-value to specialists, low-charge to
auto-approval), and target population-health investment at the diagnoses and states
driving cost. State-level median income is included as a socioeconomic covariate for
health-equity-aware reporting.

## 3. Data

Files currently in repo root (move into `data/raw/` under DVC tracking):

- `Patient_Claim_Data.xlsx` — 46,059 rows × 10 cols. Engineered by the legacy notebook
  from raw `inpatient.csv` (58,066 rows × 197 cols) and `outpatient.csv` (575,092 rows ×
  162 cols), neither of which is present in this repo (too large / not exportable —
  treat `Patient_Claim_Data.xlsx` as the ingestion boundary and don't try to regenerate
  it unless the raw files are supplied).
  - Columns: `BENE_ID` (int, repeats per beneficiary — **not a unique row key**),
    `PRNCPAL_DGNS_CD_inp` (str, ICD-10), `CLM_E_POA_IND_SW1` (str, values `Y`/`U`),
    `PRVDR_STATE_CD_inp` (int, FIPS-style state code), `Number_of_Claims_inp` (int),
    `CLM_TOT_CHRG_AMT_inp` (float), `PRNCPAL_DGNS_CD_out` (str, ICD-10),
    `PRVDR_STATE_CD_out` (int), `Number_of_Claims_out` (int),
    `CLM_TOT_CHRG_AMT_out` (float). No nulls in the merged file.
- `Median_Income.xlsx` — 51 rows: `PRVDR_STATE_CD`, `STATE`, `Median_Income`.

Target variable: `TOTAL_CHARGE = CLM_TOT_CHRG_AMT_inp + CLM_TOT_CHRG_AMT_out`.
Two modeling tasks, both worth keeping (matches legacy scope):
1. Regression on `log(TOTAL_CHARGE)` — continuous cost baseline.
2. 5-class classification of `TC_class` from `TOTAL_CHARGE`: Class 1 (<$1K),
   Class 2 ($1K–$10K), Class 3 ($10K–$100K), Class 4 ($100K–$1M), Class 5 (>$1M).
   **Check class balance on real data before finalizing bins** — Class 5 may be
   extremely sparse; if so, document it and consider class weights or collapsing rare
   tiers rather than silently reporting misleading accuracy.

## 4. Known bugs / methodology issues in the legacy R script — fix these, don't port them

1. **Encoding leakage.** Frequency encoding of `PRNCPAL_DGNS_CD_inp`/`_out` is computed
   on the *full* dataset before the train/test split, and dummy-encoding of
   `CLM_E_POA_IND_SW1` is likewise fit on the whole data. This leaks test-set
   distribution into training. Fix: fit the frequency-encoding map and categorical
   encoder on the training fold only, persist them as pipeline artifacts, and apply the
   fitted transform to test/inference data (unseen codes → a sentinel value, e.g. 0 or
   the global min frequency, not a crash).
2. **Row-level leakage across train/test via `BENE_ID`.** The same `BENE_ID` can appear
   in multiple rows (one per outpatient diagnosis). A plain random 70/30 split can put
   the same beneficiary in both train and test, inflating apparent accuracy. Fix: split
   by unique `BENE_ID` (`GroupShuffleSplit` / grouped stratified split), not by row.
3. **Inconsistent state code.** Both `PRVDR_STATE_CD_inp` and `PRVDR_STATE_CD_out` exist
   but only `_inp` is kept/renamed and merged against income; `_out` is silently
   dropped. Decide and document the rule explicitly (e.g., "state of the inpatient
   provider is used as the beneficiary's state for income context") instead of leaving
   it implicit.
4. **`CLM_E_POA_IND_SW1` dummy encoding only creates a `_Y` column** and implicitly
   treats `U` as the reference level with no explicit handling of unseen values at
   inference. Use a proper `OneHotEncoder(handle_unknown="ignore")` or an explicit
   categorical map.
5. No data validation step exists — nulls, out-of-range state codes, or malformed ICD
   codes would silently flow into modeling. Add schema validation (see §5).
6. No experiment tracking, no model registry, no served API, no tests — the entire
   project is un-reproducible outside RStudio/Colab.

Verify each of these against the actual data before fixing (don't assume — check).

## 8. Modeling standards

- Fix the leakage issues in §4 first — this is the most important engineering
  correction, and worth calling out explicitly in the README as a fixed methodology
  issue (shows judgment, not just re-implementation).
- Use scikit-learn `Pipeline`/`ColumnTransformer` so preprocessing + model are one
  serializable object — this also simplifies FastAPI serving (load one artifact).
  MLflow's sklearn flavor can log the whole pipeline.
- Log to MLflow: params, metrics (RMSE for regression; accuracy, macro-F1, confusion
  matrix, multiclass ROC-AUC for classification), the fitted pipeline, and a feature
  importance plot.
- Select the "best" classification model by a documented weighted rule (don't just pick
  highest accuracy on an imbalanced multiclass target — weight macro-F1 alongside it).
- Persist the selected pipeline to `exported_model/` (MLflow pyfunc format, like the
  sibling repo) so the API/dashboard demo works without retraining.
- Add SHAP explanations for the production classifier; surface top 3–5 contributing
  features per prediction in the API response and dashboard.
